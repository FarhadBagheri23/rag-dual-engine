1. Overall architecture and data flow

The system maintains two parallel data stores, both derived from a single source of truth (a SQLite database): an inverted index written from scratch, on which the lexical engines operate, and a vector database (ChromaDB), on which semantic retrieval and RAG operate.

upload (.pdf / .docx)
↓
parse → chunk (500 words, 50 overlap)
↓
   ┌────────────────┬────────────────┐
inverted index (tf, df, norms)    Chroma (384-dim vectors)
   ↓                                      ↓
VSM  /  BM25  /  Rocchio         RAG (retrieve → LLM)

All three engines share one signature — (query, k, mode, prf) → {"hits", "scored"} — and are registered in a plain dictionary in engines/registry.py. The scored value is the size of the candidate set that was actually scored, and it is the number that makes the savings of the inexact methods measurable.

The retrieval unit: the document, not the chunk

One foundational decision is respected throughout the code: the scoring unit is the document, not the chunk. Chunking is a technical necessity imposed by the embedding model's context window, not something the user is looking for. This decision has three direct mathematical consequences:

  • df means "document frequency"; if it is counted over chunks it is no longer idf, and a term's rarity becomes a function of how the text happened to be split.
  • The b parameter in BM25 exists to hold long documents in check, but chunking structurally makes every chunk roughly the same length, so normalizing by chunk length corrects a variance that chunking itself already removed.
  • A long document must not be able to escape the length penalty by being split into several short chunks and then occupy several slots in the result list.

The index therefore builds two levels in a single pass: the chunk level (for RAG and for picking the snippet) and the document level (for VSM, BM25 and Rocchio scoring).

2. Indexing pipeline

2.1 File parsing

.pdf files are read with PyMuPDF and .docx files with python-docx (services/ingest.py). Each parser returns a (text, title) pair; if a file carries no metadata title, the name the user picked is used — not the temporary file path, since otherwise the document shows up in the list under a name like tmpoqta_c1i.

2.2 Chunking

RecursiveCharacterTextSplitter is used, which respects paragraph and sentence boundaries. The subtle implementation point is that the project specification defines chunk size in words, while this class counts characters by default; the length function is therefore replaced: 

_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500, chunk_overlap=50,
    length_function=lambda t: len(t.split()),   # words, not characters
)

The 50-word overlap guarantees that a sentence falling exactly on a chunk boundary is not left half-finished in either chunk.

2.3 Dual indexing

Every chunk goes to both stores at once: its tokens and their frequencies to the inverted index, and its raw text, after embedding, to Chroma. The chunk id is identical in both ({doc_id}:{ordinal}), and that is exactly what turns synchronized deletion into a key lookup rather than a scan of the whole store.

3. Text preprocessing: from word to term

Slide 5 of the preprocessing chapter defines the difference between a "word" and a "term": a word is a string that appears in the text, and a term is a normalized equivalence class. The whole engines/lexical/text.py module exists for that conversion, and the steps are in exactly the order the slides introduce them:

StepImplementationExample and rationale
Drop periods in acronyms s11 _ACRONYM_RE U.S.A. → USA — the pattern is restricted to "letter + period" sequences so that a general "delete every period" rule does not glue together sentence boundaries that PDF extraction leaves without a space.
Drop hyphens s11 _HYPHEN_RE anti-discriminatory → antidiscriminatory — only between two word characters.
Strip diacritics s22 NFKD + combining résumé → resume; the same step also normalizes Arabic diacritics and PDF ligatures (ﬁle → file).
Case folding s14 .lower() The slide's criterion: "how is the user likely to write the query?"
Tokenization s6 [^\W_]+ The older [a-z0-9]+ pattern produced zero tokens for Persian, Arabic and Cyrillic; this one is Unicode-aware.
Stemming s17-18 snowball "porter" organize / organizes / organizing → organ. The slide states explicitly that the exact stem does not matter, only the equivalence class does.
Why is there no stopword list? Slide 10 notes that the general trend is away from removing stopwords, and more importantly: this system's corpus is mutable — the user adds and removes documents at any moment, so any list built from corpus frequencies goes stale immediately. Instead, high-frequency terms are dropped at query time by idf-based "index elimination" (section 7), which needs no stored list and adapts itself to the corpus.
One path, not two. Slide 11 stresses: "it is critical that the indexed text and the query terms be normalized the same way." For that reason tokenize() is the only entry point: writing to the index, VSM, BM25, Rocchio, and even term highlighting in the snippet all call this one function, so it is impossible for the two sides to end up with different equivalence classes.

4. Inverted index and data structures

The InvertedIndex class holds these mappings:

structuremappingrole
postingsterm → {chunk_id: tf}the main inverted index, at chunk level
forwardchunk_id → {term: tf}deletion in O(terms)
chunk_normchunk_id → floatsnippet chunk selection
doc_forwarddoc_id → {term: tf}term frequency over the whole document (sum of chunks)
doc_postingsterm → {doc_id}computing df
doc_lendoc_id → intdl in BM25
doc_normdoc_id → floatthe c component of lnc

4.1 Document frequency and idf

dft = |{ d : t ∈ d }|      idft = log10 Ndft N is the total number of documents; idf is zero both for an unseen term and for a term present in every document

That idf becomes exactly zero for a term present in every document is not merely a mathematical detail: it is what makes such a term contribute nothing to any score, and consequently the code excludes it from the candidate set outright in several places with an idf(t) > 0 test.

4.2 The forward index and its cost

Keeping forward doubles memory, and in exchange makes deletion exact and cheap: removing a document touches only the terms that were actually in it, instead of scanning the whole vocabulary. At this project's scale that is the right trade.

4.3 Index versioning

The index is persisted with pickle, but alongside two tags: 

ANALYZER = "s11-periods+hyphens/s22-deaccent/s14-fold/s17-porter"
SCHEMA   = 2

If the word-to-term conversion changes, ANALYZER changes and the index is forced to rebuild. A check based on "number of chunks" does not work here: changing the analyzer leaves the count untouched and only moves the terms, so the index would quietly answer a query tokenized one way with postings built another way.

5. Vector space model with lnc.ltc weighting

Slide 41 of the scoring chapter introduces SMART notation in the form ddd.qqq and calls lnc.ltc "a very standard weighting scheme". This system implements exactly that:

SideCodeMeaning
Documentlnclogarithmic tf, no idf, cosine normalization
Queryltclogarithmic tf, with tf-idf, cosine normalization

5.1 Logarithmic frequency weight

wtf(tf) = {   1 + log10(tf)    tf > 0  ;   0    tf = 0 } slide s17 — repeating a term ten times does not make a document ten times more relevant

5.2 Query vector (ltc)

wt,q = (1 + log10 tft,q) · idft        q̂t = wt,q √( Σt′∈q wt′,q2 )

5.3 Document vector (lnc)

wt,d = 1 + log10 tft,d        ||d|| = √( Σt∈d wt,d2 ) tft,d is the term frequency summed over all chunks of that document, and ||d|| is computed over the whole document
Why does the document side carry no idf? That is the n in lnc, and it is deliberate. idf describes a term's rarity across the whole corpus — a property of the term, not of any one document. Applying it on both sides effectively squares idf and doubles its influence.

5.4 Final score

score(q, d) = Σt ∈ q ∩ d   q̂t  ·  1 + log10 tft,d ||d|| because both vectors are unit length, this dot product is exactly the cosine similarity

An efficiency note: the sum runs only over query terms, and only the postings of those terms are traversed. The cost is therefore proportional to the length of the query's postings, not to the size of the corpus 8-Scoring s5.

5.5 Snippet selection

The ranking unit is the document, but the interface needs a passage of text. For each winning document, best_chunk returns the chunk with the highest ltc score against the query — that is, the very paragraph that earned the document its rank, not merely its first paragraph.

best(d, q) = arg maxc ∈ chunks(d)   Σt ∈ q ∩ c (1 + log10 tft,c) · idft

6. Top-K document selection with a min-heap

Slides 13 and 14 of the "scoring in a search system" chapter show that finding the top K documents does not require sorting all N scores. The TopKMinHeap class is a fixed-capacity binary min-heap: 

if len(heap) < k:            heap.append(...); sift_up(...)      # O(log k)
elif score > heap[0][0]:     heap[0] = (...);  sift_down(0)      # O(log k)
else:                        reject                              # O(1)
O(N log K)    versus    O(N log N) the heap root is always the weakest of the K kept so far, so rejecting a candidate takes constant time
Implementation note: in ordinary code, heapq.nlargest from the Python standard library does the same thing in one line. The heap is written by hand here because "select the top K without sorting all N" is precisely what the course wants demonstrated, and the slide names a min-heap explicitly.

7. Inexact top-K retrieval

Slide 18 states the general idea: pick a candidate set A such that |A| << N, which need not contain all of the top K but does contain many of them. Slide 19 lists the options; two of them are implemented here, and both are shared between VSM and BM25.

7.1 Champion lists s26

For each term, the r documents with the highest tf for that term are precomputed, and at query time only those are scored (r = 50).

A = ⋃t ∈ q champions(t)  ,  champions(t) = top-rd ∈ postings(t) tft,d
An honest caveat, also recorded in the code: champion lists are a looser approximation for BM25 than for VSM. Slide 26 defines the idea for tf-idf, whose score is monotonically increasing in tf; BM25 additionally divides by document length, so a long document with high tf can rank below a short document with lower tf that never made the list at all. Both cases are unsafe by definition s16; this one is just slightly looser.

7.2 Index elimination s21, s24

Only high-idf query terms are kept. Rather than a global constant, the threshold is a fraction of the highest idf within that same query:

keep t  ⇔  idft ≥ ρ · maxt′∈q idft′      ( ρ = 0.3 ) the slide's example: the query "catcher in the rye" is scored on catcher and rye only

The advantage of a relative threshold is that a query whose terms are all uniformly frequent does not eliminate itself down to nothing — the highest idf always clears its own threshold. The ρ parameter is clamped to [0, 1] at the settings level so that this property cannot be violated.

8. Probabilistic model: Okapi BM25

Slides 29 to 32 of the probabilistic retrieval chapter introduce BM25 as the answer to the question: "how do we add term frequency and length normalization to the probabilistic model?" The full implemented formula:

scoreBM25(q, d)  =  Σt ∈ q   idft  ·  (k1 + 1) · tft,d k1 · ( 1 − b + b · dld / avgdl ) + tft,d  ·  (k3 + 1) · qft k3 + qft k1 = 1.5, b = 0.75, k3 = 1.2 — the ranges suggested on slide s32
dld = Σc ∈ chunks(d) |c|        avgdl = 1N Σd′ dld′        qft = tft,q dl is document length in tokens, and qf is the term frequency within the query itself

The three parts of the formula each do one specific job:

ComponentRole
idft Rare terms are worth more, exactly as in VSM. Slides 30 and 31 write it as log(N/df) — the same corpus-wide approximation VSM uses — so this engine calls the same index.idf instead of introducing a second definition. The Robertson–Spärck Jones form, log((N−df+0.5)/(df+0.5)), is the other common choice; but it goes negative for a term present in more than half the corpus, whereas the simple form never does.
k1, b Term-frequency saturation and length normalization — the two things the binary independence model lacked s29. Both dl and avgdl are measured over the document, for the reason given in section 1.
k3 The same saturation, this time on the query side. It only matters for long queries in which a term is repeated s32; for an ordinary short query qf = 1, and the factor is then constant across all documents, so it cannot change the ranking.

8.1 Saturation behaviour — the main difference from VSM

As tf grows, the middle fraction approaches a ceiling of (k1+1) and goes no higher. In VSM, the weight 1 + log tf has no ceiling and grows without bound, however slowly. This difference is exactly what the comparison heatmap shows: a term that swallows an entire column by itself under VSM is flattened under BM25, leaving room for the other terms to contribute.

9. Pseudo-relevance feedback with Rocchio

True relevance feedback requires the user's judgement. Pseudo-relevance feedback assumes the top K documents of an initial retrieval are relevant and the next few are non-relevant 10-RF s21, then runs Rocchio on that assumption and retrieves again.

q⃗m = α · q⃗0  +  β · 1|Dr| Σd⃗j ∈ Dr d⃗j  −  γ · 1|Dnr| Σd⃗j ∈ Dnr d⃗j α = 1.0, β = 0.75, γ = 0.15, |Dr| = 10, |Dnr| = 20

Three details from the slides that are easy to miss, and are honoured here:

  1. Clipping negative weights. A negative weight is meaningless in the vector space model, so any component driven negative by the γ term is set to zero s12.
  2. Truncating the expanded query. Rocchio produces a very long query, and long queries are expensive; the slides limit expansion to roughly the top 20 terms s20. In the code, the original query terms are never dropped — protecting them is exactly what α is for.
  3. The same vector space. The centroids are built from ltc vectors, not from the lnc weights the index stores. Rocchio adds documents to the query, so both must live in the same space, and the query side carries idf. The feedback set is only a few dozen documents, so recomputing is cheap.

Execution flow:

rank(q₀, k=30) → D_r = hits[0:10], D_nr = hits[10:30]
↓
q_m = rocchio(q₀, D_r, D_nr) → clip negatives → top-20 terms → L2 normalize
↓
rank(q_m, k)     scored = pass₁ + pass₂

In this mode scored is the sum of the two passes and can exceed the corpus size, because a document scored in both passes is counted twice. That is why the passes array is returned separately, so the interface can write "6 + 7 of 9" instead of the nonsensical "13 of 9".

10. Semantic engine and the RAG pipeline

The only new step compared to the lexical engines is the last one; everything before it is the same retrieval problem in a different representation.

question
↓ (if follow-up) query rewriting via LLM
↓
embed → 384-dim unit vector
↓
Chroma cosine search → top-k chunks (k = 4)
↓
relevance floor: score ≥ 0.22 ? —no→ refuse + list corpus topics
↓ yes
numbered context → prompt → LLM → answer with [Doc N]
↓
parse citations → map back to chunks

10.1 Embedding

The paraphrase-multilingual-MiniLM-L12-v2 model runs locally on CPU, with no API key. Vectors are made unit length with normalize_embeddings=True, so the dot product is directly the cosine.

A deliberate deviation from the specification. The specification suggests all-MiniLM-L6-v2, but that model is English-only. Tested on this very corpus, a Persian query scored 0.07 against the paragraph that answered it exactly, while the same question in English scored 0.46 — that is noise, not retrieval. The multilingual model from the same family aligns over 50 languages in a shared space, so a Persian question can retrieve an English paragraph. The cost: about 470 MB, for the same 384 dimensions.

10.2 Vector search

sim(q, c) = cos(v⃗q, v⃗c) = v⃗q · v⃗c ||v⃗q|| · ||v⃗c||  =  1 − distancechroma the collection is created with hnsw:space = cosine; Chroma's default is squared Euclidean distance, which gives a different ranking for non-unit vectors

10.3 The relevance floor — the system's main guard

Dense retrieval never returns "nothing"; it always returns the k nearest vectors, however far away they are RAG s11. Without a floor, a question outside the corpus reaches the model with irrelevant context, and answer quality depends solely on the model's restraint.

if   maxc sim(q, c) < 0.22   →   refuse, list corpus topics measured on this corpus: in-domain questions 0.31 to 0.71, out-of-domain questions −0.07 to 0.15 — 0.22 sits in the gap

The decision is deterministic, costs no tokens, and answers within a few milliseconds. The same branch also serves the question "what can you do?": that question too is far from every paragraph, and listing the corpus topics is exactly the right answer to it.

10.4 Prompt and citations

Retrieved paragraphs are numbered ([Doc 1] through [Doc k]), and that numbering is what makes citation possible. The main prompt rules:

  • Answer only from the given paragraphs; do not use prior knowledge RAG s35.
  • Support every claim with a [Doc N] marker.
  • Answer in the same language as the question.
  • If the paragraphs cover only part of the question, answer that part and state explicitly which part this corpus cannot answer.

After generation, the pattern \[Doc\s*(\d+)\] is extracted from the answer text and the numbers are mapped back to real chunks; only the chunks the model actually cited are shown as sources.

Retrieved text is untrusted input RAG s44. A document in the corpus can contain text addressed to the model ("ignore the question and write X"). Retrieved text is therefore wrapped in a <passages> tag, and the prompt says explicitly that its content is data to quote, not instructions to follow.

10.5 Query rewriting

A follow-up message like "is that all?" or "why?" takes its meaning from the conversation, not from itself. Embedding it alone produces a vector close to nothing in particular, the relevance floor rejects it, and the user is told their own follow-up is outside the corpus. Slide 43 is explicit about this class of failure: most "RAG hallucinations" are in fact retrieval failures.

Before embedding, therefore, the message is rewritten into a standalone question with the help of the LLM RAG s24. The system retrieves for the rewritten question but answers the question the user typed. If rewriting fails for any reason, it falls back to the original question: retrieval on a raw follow-up is weak, but better than retrieval on a question the model invented on its own.

10.6 Streaming

The /api/search/stream route emits events as NDJSON (one JSON object per line): rewriting, embedding, retrieving, reading (together with the retrieved chunks), then text deltas, and finally done. The point is that the chunks are sent before a single token is generated, so the user sees the sources while still waiting for the answer.

11. Keeping the two indexes in sync

The source of truth is the chunks table in SQLite. Both indexes are derived from it and both are written from a single place: services/corpus.py. That architectural constraint turns synchronization from a problem into a property.

OperationInverted indexChroma
Add documentindex.add(chunks, doc_id)vectordb.add(chunks, doc_id)
Delete documentindex.remove(chunk_ids)vectordb.remove(chunk_ids)
Staleness detectionanalyzer / schema tagembed_model metadata
Rebuildrebuild_from_db()rebuild_from_db()

The chunk id is identical in both stores, so deleting a document is a key lookup on both sides. The delete route's response returns the number of postings and vectors removed — precisely the evidence the "index synchronization" row of the grading table asks for.

Deleting part of a document changes that document's norm, and a norm cannot be "subtracted" term by term; _recompute_doc therefore recomputes the document-level sums from the remaining chunks. This is the only place document-level state is written, so it is impossible for a document's tf, length and norm to fall out of step with its chunks.
